# 自动化/工作流固定运行入口与按次追问设计

日期：2026-11-19  
状态：待用户批准

## 1. 背景与意图

当前普通自动化任务每执行一次就创建一个新会话，`automationRun.sessionId` 指向该会话；用户必须进入运行历史再跳转，且同名运行会话会持续进入普通会话树。工作流运行则在 2026-10-28 后刻意去会话化，结果保存在 `automationRun.graphTrace` 与 `graphRunNode`，没有可持续追问的会话。

目标是参照 WorkBuddy 的使用方式：左侧会话树为每个自动化任务提供固定入口，为有运行记录的工作流提供固定入口；右侧通过执行时间切换各次结果，并允许从选中的执行继续追问。公开资料只能支持 WorkBuddy「每次执行独立会话」的语义，不把其内部表结构当作已验证事实。

已确认的核心语义：

1. 用户看到的是固定入口，底层仍是一次运行一个独立会话。
2. 每次运行是可查看、可继续对话的检查点。
3. 追问归属于所选运行，切换回该运行后仍可见。
4. 后续定时/事件/webhook 执行仍从任务原始配置独立开始，不读取历史运行或人工追问。

## 2. 目标、非目标与反目标

### 2.1 目标

- 一个自动化任务在会话树中只占一个固定条目，不再为每次运行平铺同名会话。
- 有运行记录的工作流也有固定条目；挂在自动化任务上的图运行只归入任务条目，不在工作流条目重复出现。
- 默认打开最近一次运行；可按执行时间、状态、触发类型和重试次数切换。
- 普通任务运行直接复用已有 `run.sessionId`；工作流运行在首次追问时创建伴随会话。
- 对失败运行也允许追问，用于分析错误；运行中和跳过态不允许追问。
- 保留现有运行历史，继续承担跨任务筛选、统计、失败排查和审计。
- 兼容既有运行记录、会话深链、运行保留策略和本地/远程主机数据源。

### 2.2 非目标

- 不把历次运行合并成一个物理会话，不给 `message` 增加运行分区字段。
- 不改变调度、补跑、重试、并发互斥和无人值守权限语义。
- 不把人工追问自动加入任务 prompt，也不让后续运行继承追问。
- 不在追问时自动重新执行工作流；追问是普通聊天，不修改图定义或运行记录。
- 不删除现有运行历史页，不在本期新增移动端固定入口 UI。

### 2.3 反目标

- 所有运行消息在一个长消息流中混合展示。
- 为保留固定入口而永久保留已被运行保留策略删除的运行元数据。
- 让用户无法判断当前正在查看或追问哪一次执行。
- 为支持追问而恢复「工作流每个节点消息对落聊天会话」的旧模型。

## 3. 方案比较与选择

### 方案 A：固定聚合入口 + 每次运行独立会话（已选择）

侧边栏条目是任务/工作流的聚合视图。切换执行时间即切换该次运行已有的会话；追问留在该会话。工作流仍由运行轨迹表提供结果，只在首次追问时补充伴随会话。

优点：运行隔离天然成立；现有普通任务会话可以直接收编；无需迁移消息；后续自动执行不会误读追问。代价：需要稳定的会话分组元数据、聚合路由和工作流伴随会话创建链路。

### 方案 B：一个物理会话 + 消息按运行编号过滤

所有运行与追问写入同一个 `session`，再给消息增加运行归属并按运行过滤。

不选择的原因：需要改消息 schema、消息加载、上下文组装和历史迁移；误把追问带入后续自动执行的风险更高；与已确认的独立检查点语义不一致。

## 4. 用户交互

### 4.1 左侧固定入口

会话树新增「自动化与工作流」分组，和普通空间/项目会话分开：

- 每个现存自动化任务对应一个条目，即使尚未运行也可打开空态。
- 每个至少有一次顶层运行或已有追问会话的工作流对应一个条目。
- `run.taskId != null` 时归任务；仅 `taskId == null` 的顶层图运行归工作流。子工作流节点不生成条目。
- 条目标题取任务/工作流当前名称，附类型图标和最近运行状态；按最近运行时间排序，未运行任务按创建时间排在有运行条目之后。
- 固定条目不提供普通会话的重命名、置顶、归档和批量删除。菜单提供「打开任务/工作流」「立即运行」（任务）和「查看运行历史」。
- 被聚合的运行会话不再作为普通会话重复出现；全局搜索仍能找到其中的消息，但落点进入对应固定入口和运行。

### 4.2 右侧运行切换

固定入口使用独立 URL 参数，保证刷新、搜索和历史跳转可恢复：

- 任务：`/module/ai?automation=<taskId>&run=<runId>`
- 顶层工作流：`/module/ai?graphRun=<graphId>&run=<runId>`
- 缺省 `run` 表示最近一次运行。

会话顶栏右侧增加运行选择器，位于会话搜索之前。当前项展示执行时间和状态；弹层按时间倒序列出触发类型、状态、耗时和第几次重试，并沿用现有分页查询，避免一次加载全部轨迹。

普通 `?session=<id>` 深链保持可用：若会话关联运行，则解析为对应固定入口及 `runId`；否则维持普通聊天行为。

### 4.3 结果与追问

- **有原始会话的普通任务运行**：直接显示现有 `ChatPane`，其中包含自动执行消息和此后的追问。
- **工作流运行**：上方显示可折叠的最终输出/错误摘要和现有 `GraphRunTraceView`，下方显示该次运行的伴随会话；未创建伴随会话时只显示输入区。
- **早期失败、尚未有会话的普通任务运行**：显示运行错误；首次追问时补建伴随会话。
- **running/skipped**：只显示当前状态或跳过原因，不显示追问输入。
- 运行选择器始终可见；切换运行不会中止其他会话中正在进行的追问，流式状态仍按真实 `sessionId` 隔离。

## 5. 数据模型与归属

不合并现有会话，新增的是稳定分组和补建会话所需元数据。

### 5.1 session

增加两个可空列：

- `automationTaskId Int?`：该会话归属于哪个自动化任务的运行集合；prompt 运行和 graph 任务的伴随会话都使用。
- `runGraphId Int?`：仅顶层工作流运行的伴随会话使用，值为 `graphDefinition.id`。

两者不得同时非空；普通会话两者均为空。`graphDefinition.aiSessionId` 仍只表示 AI 编排会话，绝不与 `runGraphId` 混用。为两列分别加普通索引，`SessionRecord` 透出两字段供会话树分组和深链解析。

`SessionRecord` 另以只读派生字段 `automationRunId?: number` 暴露当前会话关联的运行，不新增重复物理列；来源仍是 `automationRun.sessionId`。

### 5.2 automationRun

- 继续以 `sessionId` 表示该次运行当前唯一的聊天/伴随会话。
- 增加 `workspaceId Int?`，在图运行建行时记录实际执行空间，供多年后首次追问仍在原工作空间补建会话。普通任务运行也可写入，便于失败无会话时补建。
- `sessionId` 建唯一索引（数据库允许多个 NULL），从存储层保证一次运行不会因双击/并发创建多个伴随会话；迁移前先核验既有数据无重复。

### 5.3 新建与回填

- 普通任务 `createSession(task)` 同时写 `automationTaskId=task.id`。
- 图运行 `createRunRow` 写实际 `workspace.id`。
- 首次追问时按运行归属写 `automationTaskId` 或 `runGraphId`，再原子写回 `run.sessionId`。
- 发布前 schema 变更按桌面端 v1 快照与指纹守卫惯例处理；server 同步 SQLite/PostgreSQL schema 与迁移。
- 既有 prompt 会话经 `automationRun.sessionId → taskId` 回填 `automationTaskId`，不合并、不改消息。
- 既有顶层图运行没有工作空间列，不回填猜测值；首次追问优先使用图 AI 编排会话的工作空间，仍无法确定时要求用户选择一次工作空间。
- 运行行早已删除而无法反查任务的旧会话保持普通会话，不做启发式标题归组。

## 6. 固定入口与运行查询 API

新增统一的运行分组读模型，避免侧边栏为构造入口拉取全部运行：

```ts
type RunGroupRecord = {
  kind: "task" | "graph";
  ownerId: number;
  name: string;
  workspaceId?: number;
  projectId?: number | null;
  latestRun?: RunRecord;
  hasRuns: boolean;
};
```

`AutomationApi.runGroups()` 本地走 IPC，远程走无头端等价端点。任务组由任务表生成；图组仅包含有顶层 run 或 `runGraphId` 会话的图。所有查询经当前用户归属过滤，任务和图的 ID 不跨类型混用。

另增加：

- `AutomationApi.runById(runId)`：深链和选择器定位指定运行，校验任务/图归属；不要求目标位于当前分页第一页。
- `AutomationApi.runBySessionId(sessionId)`：旧会话深链规范化；也可由 `SessionRecord.automationRunId` 替代独立请求。
- `AutomationApi.ensureRunSession(runId, workspaceId?)`：终态运行的幂等伴随会话创建；已有 `sessionId` 直接返回。

运行列表继续复用 `AutomationApi.runs(page, taskId, status)` 和 `GraphApi.runs(graphId, page)` 的分页能力，不复制轨迹存储。

## 7. 伴随会话创建与追问上下文

`ensureRunSession` 在主进程/server 服务层完成，前端不直接拼会话归属：

1. 校验 run 属于当前用户，且状态不是 running/skipped。
2. 若已有 `sessionId`，返回既有会话。
3. 解析工作空间：任务运行使用 `task.workspaceId`；顶层图运行使用 `run.workspaceId`；历史图运行按 §5.3 的回退规则处理。
4. 项目任务继承 `projectId`，由既有会话创建逻辑解析项目资产空间；标题使用任务/图名和执行时间。
5. 创建普通 agent 会话并写分组列，同事务占住 `run.sessionId`；唯一冲突时读取并返回胜者，不向用户报错。
6. 会话创建成功但第一次发送失败时保留空伴随会话，下次追问复用，不重复创建。

追问仍走现有 `ChatApi.send`，不经过 automation scheduler 或 graph executor。聊天服务在发现会话被 `automationRun.sessionId` 引用时注入固定的运行摘要上下文：

- 公共字段：任务/图名、运行 id、执行时间、触发类型、状态和错误。
- prompt 运行已有消息历史时以该历史为主，不重复注入完整消息。
- 无原始消息的早期失败运行注入错误摘要。
- graph 运行注入最终输出、失败节点详情和按节点排序的受限轨迹摘要；完整轨迹仍在 UI 中查看。
- 运行摘要必须确定性截断，优先保留最终输出与错误，不能把每个节点 64KB 上限内容无界塞入上下文。
- 该注入只发生在用户主动追问的 `ChatService.send`；自动执行的 `automation-runner`/`graph-executor` 不读取此上下文。

后续定时执行继续调用原有 `createSession(task)` 和原始 prompt/图输入，因此从机制上不会携带此前运行或追问。

## 8. 删除、保留与异常生命周期

- 固定条目不是额外资源，删除任务/图仍在原有管理页完成。
- 删除任务或图时，沿用当前「删运行但不删聊天内容」的行为：先解除相关会话的分组字段，再删运行；这些会话回到普通会话树，避免用户追问随运行元数据被静默删除。
- 运行保留策略删除 run 前同样解除其会话分组；消息和会话本身不删除。被裁剪运行不再出现在时间选择器中。
- 用户经其他入口删除某个追问会话时，沿用 `deleteSession` 将 `run.sessionId` 置空；运行仍在，下一次追问可重新创建伴随会话。
- 选中运行被删除、任务/图被删除或切换主机时，固定入口回到对应组最近运行或安全空态，不保留死链。
- 普通会话的重命名、归档、置顶不传播到固定条目；固定条目名称始终跟随任务/图。

## 9. 本地、远程与移动端

- 桌面本地走新 IPC；无头 server 提供同形状只读/补建端点，`remote-catalog` 做既有形状转换。
- 协议新增 `runSessions` 能力标记。只有远程主机上报该能力时启用固定入口、旧深链规范化和伴随会话补建；旧无头端继续显示原有普通会话和运行历史，不因 404 破坏聊天。
- server 的自动执行同样保持每次运行独立会话，并写相同分组字段；否则远程固定入口无法收编新运行。
- 移动端现有运行记录和会话 API 只接收新增可空字段，不新增移动 UI；本期不改移动导航。

## 10. 事件、缓存与状态

- 调度/运行完成沿用 automation、graph、session changed 事件，统一失效 `runGroups`、对应 runs 分页和 `sessions` 查询。
- 新运行完成时固定条目更新最近状态；若用户正在查看该固定入口且未主动选择历史运行，可跟随到最新运行；一旦 URL 中显式选择了 `run`，新运行只更新选择器，不打断当前阅读或追问。
- 伴随会话补建后失效 sessions、runGroups 和该 run 查询，再进入真实会话发送链。
- 所有流式状态继续按真实 sessionId 管理，不能以固定条目 ownerId 作为流键。

## 11. 验收与测试

### 11.1 核心验收

1. 同一任务连续运行三次，会话树只有一个固定条目；右侧可切换三次结果。
2. 在第一次运行追问后切到第二次再切回，第一次的追问仍在，第二次看不到它。
3. 第四次定时运行只收到任务原始 prompt，不包含任何历史运行输出或人工追问。
4. 工作流运行无需恢复节点消息会话即可查看完整轨迹；首次追问后生成一个伴随会话，重复点击不会生成多个。
5. 失败运行可追问，running/skipped 不可追问。
6. 旧 `?session=` 链接、运行历史跳转和全局搜索都落到对应固定入口及正确运行。
7. 运行保留删除或任务/图删除后，已有追问内容不丢，会话按 §8 回到普通树。
8. 本地和支持新能力的远程主机行为一致；旧远程主机保持现有行为。

### 11.2 自动化测试层

- 纯函数：运行分组、任务/图去重、最新运行选择、固定入口排序、运行状态可否追问。
- 会话树：固定条目与普通会话不重复，组折叠/选中态/搜索落点正确。
- ChatView/RunSessionView：URL 恢复、显式 run 不被新运行抢占、不同 sessionId 流式状态隔离。
- repo/service：用户归属校验、工作空间解析、幂等补建、唯一冲突重读、历史图运行回退。
- 上下文：graph 摘要截断与错误优先；scheduler 输入不受追问影响。
- 生命周期：retention、删任务、删图、删会话后的归属和死链处理。
- 契约：本地 IPC、server SQLite/PG、remote-catalog 和旧能力回退。
- E2E：自动运行 → 固定入口 → 历史运行追问 → 新一次运行，验证上下文隔离。

## 12. 实现者可自行决定的事项

- 新组件的文件拆分和 `RunSessionView` 内 trace/ChatPane 的具体布局，只要不改变上述交互与状态语义。
- 运行选择器使用分页弹层或渐进加载，以及复用现有 RunRow/Badge 的程度。
- 查询 key 名称和事件去重细节。
- 运行摘要的具体 token/字符预算，但必须有上限、确定性测试，并优先保留最终输出与错误。
- Prisma 的具体迁移步骤按桌面/server 各自现有约定执行，不改变本文数据语义。
- 是否以 `SessionRecord.automationRunId` 替代单独的 `runBySessionId` 请求。
